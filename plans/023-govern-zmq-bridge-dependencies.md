## Why this matters
The runtime-critical bridge has its own npm lock outside Bun workspaces. Dependabot covers only root Bun dependencies, and Docker runs `npm install`, which can drift from the checked-in lock.

## Current state
- `scripts/zmq-rawtx-bridge/package.json:1-8` pins `zeromq` and has an isolated `package-lock.json`.
- `Dockerfile:40-42` runs `npm install --omit=dev` instead of lock-enforcing `npm ci`.
- `docker-compose.local.yml:135-136` also installs the bridge with `npm install` on startup.
- `.github/dependabot.yml:3-50` covers root Bun, Actions, Docker and Compose but not npm in the bridge directory.

## Scope
**In scope**
- Bridge `package.json`/`package-lock.json`.
- Dockerfile and local Compose install commands.
- Dependabot and CI/security workflow.
- A minimal bridge package smoke check.
- `plans/README.md` (status only)

**Out of scope**
- Running native zeromq inside Bun.
- Rewriting the bridge.
- Merging npm and Bun lockfiles.

## Steps
1. Validate/regenerate `package-lock.json` with a supported Node/npm version and confirm it contains only the bridge dependency tree.
2. Change both Dockerfile and local Compose startup to `npm ci --omit=dev --prefix scripts/zmq-rawtx-bridge` so production and development exactly follow the lock.
3. Add a Dependabot `npm` entry for `/scripts/zmq-rawtx-bridge`, grouped/labeled consistently.
4. Add CI/security steps using a pinned Node version: lockfile install/audit and a minimal module/startup smoke that does not require a live Dogecoin endpoint. Build the production image as the native compilation gate.
5. Document how to update/audit both package ecosystems.
